# Operational readiness review

Baseline: `bce9d978`. Repository review only; no load traffic, production settings changes, MFA enrollment or provider retention verification was performed.

Later September 14 update: [administrator MFA implementation](admin-mfa-implementation-2026-09-14.md) is now prepared and locally verified. The findings below describe the deployed baseline; production MFA rollout remains pending.

| Area | Finding | Required evidence / next implementation |
| --- | --- | --- |
| Platform-admin MFA | OPEN. `backend/src/admin-operations/admin-access.guard.ts` checks authenticated identity and current database ADMIN role. No MFA proof is checked; no enrollment/challenge/recovery implementation was found in current auth code or migrations. An OTP input component alone is not MFA. | Implement enrollment and server-verified, session-bound step-up before platform-admin operations, covering existing sessions, expiry, replay rejection, throttling, recovery and removal. Preserve ordinary user access while preventing admin access until verification. Test all admin boundaries and recovery before rollout. Provider-account MFA is not Itemize step-up. |
| Load and capacity | NOT VERIFIED. CI runs correctness/build/audit gates without a current API load gate. `scripts/canvas_benchmark.js` imports deleted Express routes, substitutes authentication and truncates a fixture table using an environment-selected database. The mock variant is not deployed capacity evidence. | Build a disposable current-Nest/PostgreSQL harness with synthetic tenants and real authentication. Measure bounded reads/writes, concurrency, p50/p95/p99, throughput, errors/429s, database pool pressure and post-load consistency. Start with 1/5/10 users on isolated infrastructure; define launch traffic assumptions and latency budgets before interpreting capacity. Never aim the legacy script at production. |
| Error monitoring | PARTIAL. API `main.ts` and frontend `lib/sentry.ts` initialize Sentry when configured. Earlier evidence establishes variable presence, not event receipt or alerts. | Send a controlled sanitized exception through each actual error path; verify receipt/release/environment and alert acknowledgement. Review capture wiring and secret/PII scrubbing before adding telemetry. |
| Log retention | NOT VERIFIED. Railway logging is described in platform docs, but no earliest retrievable log, retention setting/export evidence or alert acknowledgement is recorded. Sentry initialization does not establish retention. | Record provider/project settings, authorized access, earliest retrievable sample and a sanitized retrieval exercise. Determine requirements and costs before adding storage or cleanup. Do not invent a retention period or delete audit/evidence data to enforce an unapproved policy. |
| Incident response | PREPARED, UNDRILLED. Existing security checklist requested a procedure; the API guide still referred to retired Express. | Current [incident response](Deploy/incident-response.md) and [API recovery](Deploy/production-api-restore.md) are documented. Run a tabletop, confirm coverage/notification owners and record results before marking readiness passed. |

The release guide was corrected to current Nest/database paths, actual gate responsibilities and preserved worker ownership. These documentation changes do not close MFA, load, telemetry or retention verification. Backup/PITR and SMS remain deferred by the user.

Recommended implementation order: platform-admin MFA, a disposable load harness, then verified monitoring/retention and an incident tabletop. No production credential, permission or paid service change is implied by this review.
